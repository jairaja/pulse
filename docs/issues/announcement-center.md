# Multilingual in-app announcements for guests and accounts

Design/specification only. Do not implement the app, announcement database, publisher or jobs in the language/preferences change. This is separate from FCM/APNs push notification delivery (T12): checking on open/foreground and manual refresh is sufficient.

Recommended UX:

- Home top-right bell, accessible label and generous touch target. A small green dot signals new items; include an accessible “new announcements” state, not color alone.
- Tapping opens a full-height screen sliding from the right. This better accommodates translated paragraphs, large text, small devices, safe areas, screen readers and pagination than a small dropdown. Show heading, close/back, refresh top-right, scrollable list, loading/empty/offline/error states, and last successful refresh. Keep existing list visible during refresh; prevent duplicate refresh requests.
- Tap a list item to show detail as a sheet/modal above the list. Closing it restores the list's scroll position, filters and refreshed items. Android Back closes detail first, list second. Screen-reader focus enters detail and returns to its list item. External links are explicit and allowlisted, never executed from arbitrary announcement markup.
- Signed-in accounts: unread rows have stronger emphasis, read rows muted but fully interactive. Detail offers explicit **Mark as read** or **Mark as unread**, with the current status explained; either saves then closes. On failure show retry and keep the detail open; do not falsely report saved status. Merely opening a detail does not override the explicit choice. Read states follow the account across devices and survive reinstall/sign-in.
- Guests: neutral rows without read/unread controls. Detail has **Okay**. A device-local last-seen feed revision drives only the bell dot, not per-item read state. Mark the captured list revision seen when the list opens; announcements arriving later retain the dot. On reinstall/new device, guests see current announcements as new.
- Optional dropdown alternative must support outside-tap dismiss only when no detail is open, preserve the dropdown behind detail, trap/restore focus correctly, and expand to full-screen for large text. Prefer one full-screen behavior for the initial release. See the editable SVG mockup in `docs/design/announcements-proposal.svg`.

Delivery and storage:

- Superuser-only draft/publish/withdraw. Original text + source language + immutable source version; server-side AI translations stored per locale/version. No translation API call or secret in a client read. Review/completeness gate before publication. A newer source version invalidates old translation readiness; users must not see mismatched translation versions. An explicitly missing locale shows a labelled original-language fallback.
- Published/scheduled/expired/withdrawn lifecycle, starts_at/ends_at in UTC. Serve only authorized live content. Expired/withdrawn/deleted content must disappear from caches. A scheduled future announcement must not leak through a public feed before release.
- Do **not** send every cached timestamp. Use a bounded delta endpoint with opaque cursor encoding feed epoch, committed revision and locale. Return changes (versioned upserts/tombstones), next cursor, pinned committed high-water revision, server_time, nearest transition, and whether a full snapshot is required. Limit pages (for example 100) and payload size; deduplicate by announcement ID and apply only increasing per-item revisions.
- Critical: a plain sequence/nextval is allocation-ordered, not commit-ordered. Transaction A can allocate 100, B commit 101, client checkpoint 101, then A commits 100 and is lost. Use a transactional counter locked through commit for this small broadcast feed, or an equivalent change stream with a proven committed checkpoint. A cursor must never jump an uncommitted gap. Add an index on committed revision and retain tombstones/change records for the offline window.
- Initial consistent snapshot pins a watermark, pages live content, then catches changes after that watermark. Apply pages and advance cursor atomically in the device store; failures/retries must not lose events. Respect expired cursors/changed feed epochs with explicit snapshot reset; never return a misleading empty delta. Translation-language changes reset the language-scoped snapshot rather than reusing another locale's body.
- Publication, translation correction, withdrawal, activation and expiry create lifecycle revisions. Check visibility against server time on every response; return the next transition for a client timer. Foreground and bounded TTL/manual refresh recover missed activation jobs. Do not rely on an expiry write/event alone to stop showing expired content. Avoid timer dependence on an untrusted device clock.
- Cache public announcement content by project/locale/feed epoch. Store read state separately by authenticated account with indexed `(user_id, announcement_id)` and owner-checked RPCs/RLS. Track the last acknowledged content revision too: a substantive newly published revision becomes unread again, while a translation-only correction follows an explicit policy. Server changes to read state have their own version/checkpoint; public content cursor alone cannot synchronize read/unread across devices. Versioned updates resolve races deterministically, with idempotent retries; never replay account A's pending mark under account B.
- On app startup/foreground fetch a bounded delta, deduplicate in-flight pulls, use ETag/304 where appropriate, backoff + jitter on failures, retain valid cached content, and use a bounded retry interval while the screen is open. No permanent per-guest server identity is necessary. No background polling promise while the OS suspends the app.

Design-model stress validation:

Run `node docs/design/announcement-sync-model.mjs`. The deterministic local simulation processed 100,001 committed changes with page size 100, duplicate delivery, stale replay, concurrent arrivals while paging, equal timestamps, allocation-vs-commit ordering, cursor retention/epoch reset, locale scope, account read isolation and scheduled visibility/expiry. Final cached content matched the server model. For 10,000 known notices, a JSON timestamp list was 558,891 bytes versus 60 bytes of cursor metadata (responses excluded). Local run was about 0.1 seconds; this is neither a hosted load test nor a production latency target.

Future acceptance/load tests: real PostgreSQL transactional counter and aborted transactions, simultaneous publishers/readers, large payloads and translated text, rollout fan-out and CDN hit rate, snapshot consistency, log compaction, 30+ day offline devices, clock drift, missing translations, screen-reader/RTL/large-font behavior, read-state races between devices, logout/revocation during save, account switches, airplane mode and repeated refresh. Define latency/error/retention/payload budgets before implementation. Preserve immutable audit history and server-owned role checks. Link language, admin/superuser and single-device-session issues.
